# Diseño aprobado del MVP v0.1

## Resultado

El MVP será una aplicación real y publicable que combina portafolio profesional, catálogo de servicios, captura segura de solicitudes y backoffice autenticado. Se construirá en incrementos verticales sobre el stack aceptado en `docs/adr/0001-stack.md`.

## Principios

- El portafolio público no depende funcionalmente de operaciones.
- Datos privados nunca se derivan por exclusión. Cada interfaz pública usa una allowlist.
- Autorización se comprueba en servidor para REST, Local API, rutas Next, medios, sitemap y panel.
- Un solo administrador en v0.1.
- Sin pagos, facturación, reservas, inventario, portal de clientes ni reapertura de solicitudes.
- Datos sintéticos hasta aprobar contenido, privacidad y retención.
- POC y evidencias históricas permanecen intactas.

## Enfoques evaluados

### Scaffold limpio y riesgo primero

Seleccionado. Porta contratos, invariantes y pruebas útiles, no estructura experimental. Primero entrega intake y privacidad; después completa operaciones, contenido y diseño.

### Scaffold limpio y portafolio primero

Descartado como orden principal. Produce una superficie visible antes, pero posterga PII, depende de contenido real aún no disponible y deja tarde el riesgo técnico mayor.

### Promover POC

Descartado. Mezcla producto con arneses experimentales y un gate Docker inconcluso.

## Arquitectura

Una aplicación Next.js/Payload y una base PostgreSQL forman un monolito modular desplegable en contenedor.

| Módulo | Responsabilidad | Dependencias permitidas |
|---|---|---|
| `identity` | Admin único, sesión, autorización y procedimiento de recuperación | Payload Auth |
| `content` | Perfil, proyectos, publicación, preview y medios | `identity` |
| `catalog` | Servicios públicos, activación, precio y orden | `identity` |
| `intake` | Formulario, validación, CSRF, abuso, idempotencia y creación | `catalog`, persistencia transaccional |
| `operations` | Bandeja, observaciones, estados, motivos y eventos | `identity` |
| `public-site` | Rutas públicas, DTO, HTML, SEO y estados vacíos | gateways de `content`, `catalog` e `intake` |
| `observability` | Correlación, eventos y redacción | metadatos sin PII |
| `deployment` | Imagen, migraciones, healthcheck, backup y restauración | infraestructura |

`content` no depende de `intake` ni `operations`. Una falla operacional no debe impedir consultar el portafolio publicado.

## Modelo

### Editorial

- `UsuarioAdmin`: identidad administrativa sin interfaz pública de alta o recuperación.
- `Perfil`: singleton con presentación, experiencia, formación, competencias y enlaces autorizados.
- `Proyecto`: título, slug, resumen, contenido, tecnologías, enlaces, SEO, publicación y medios públicos.
- `Servicio`: nombre, slug, descripción, categoría, modalidad de precio, orden y estado activo.
- `MedioPublico`: archivo publicable y texto alternativo.
- `MedioPrivado`: archivo administrativo no referenciable desde documentos publicados.
- `AjustesSitio`: SEO global y canales autorizados.

### Operaciones

- `Solicitud`: nombre, contacto, tipo de equipo, descripción, servicio opcional, estado, motivo de cierre, observaciones internas y timestamps de servidor.
- `EventoSolicitud`: solicitud, estado anterior, estado nuevo, actor, fecha y motivo. Sólo inserción.
- Registros internos de nonce e intentos antiabuso, inaccesibles desde API pública.

Estados válidos:

```text
recibida -> en_gestion -> cerrada
recibida -------------> cerrada
```

`cerrada` es terminal. Cerrar exige `atendida`, `descartada`, `duplicada` o `spam`. No existe reapertura.

## Flujos

### F1: descubrimiento profesional

Rutas: `/`, `/sobre-mi`, `/proyectos`, `/proyectos/[slug]` y `/contacto`. Server Components consultan gateways públicos con `overrideAccess: false`, usuario anónimo y borradores desactivados. El gateway devuelve DTO por allowlist. Un borrador y un slug inexistente producen el mismo 404.

### F2: solicitud pública

`GET /servicios/solicitar` genera formulario no cacheable, nonce firmado y cookie `__Host-*` con `Secure`, `HttpOnly` y `SameSite=Strict`. `POST /api/intake` valida tipo y tamaño, origen, CSRF, campos, servicio activo, honeypot, tiempo mínimo, límite e idempotencia. La persistencia reserva nonce, consume límite y crea una solicitud `recibida` dentro de una transacción. La respuesta de éxito es genérica y no contiene identificador ni estado interno.

### F3: administración de contenido

Admin inicia sesión en `/admin`, crea borrador, previsualiza, publica y retira sin borrar. Contenido publicado aparece sin commit. Medios privados nunca se relacionan con documentos públicos.

### F4: gestión interna

Admin filtra solicitudes por estado o motivo, revisa detalle, cambia observaciones y ejecuta transiciones. Cada transición válida crea exactamente un evento en la misma transacción. Eventos no se editan ni borran por API.

## Seguridad y privacidad

- Acceso denegado por defecto en colecciones y campos.
- GraphQL desactivado y verificado como cerrado.
- Local API pública siempre con `overrideAccess: false`.
- Recuperación pública de contraseña deshabilitada.
- Admin creado por CLI o tarea local antes de exponer puertos.
- Proxy es única entrada HTTP: elimina cabeceras de IP aportadas por cliente, inserta `x-jozeuzz-client-ip` y mantiene aplicación en red privada sin puerto publicado.
- Entrada pública acepta sólo campos enumerados; campos administrativos producen rechazo.
- Límites antiabuso proporcionales, sin servicios externos en v0.1.
- Logs no incluyen nombre, contacto, descripción, cuerpo, query SQL, parámetros ni stack.
- Retención y borrado se documentan antes de usar datos reales.
- Secretos permanecen fuera de Git e imágenes.
- Rutas administrativas envían `frame-ancestors 'none'` y `X-Frame-Options: DENY`; CSP completa se valida con Payload antes de endurecerla.

## Errores

| Caso | Respuesta pública |
|---|---|
| Contenido ausente o no publicado | 404 indistinguible |
| Validación | 400 con errores sólo para campos públicos |
| Origen o CSRF inválido | 403 genérico |
| Límite excedido | 429 con `Retry-After` |
| Reintento del mismo nonce | confirmación genérica sin duplicar |
| Servicio inactivo | 400 asociado al campo `servicio` |
| Fallo interno | 500 genérico con identificador de correlación |

Un fallo transaccional revierte nonce, límite, solicitud, estado y evento según corresponda.

## Interfaz visual

Dirección “Técnica precisa”:

- tipografía del sistema; monoespaciada sólo para metadatos;
- fondo claro, superficies gris frío, azul para interacción y violeta para área técnica;
- contraste WCAG 2.2 AA con margen;
- foco visible separado por 2 px;
- componentes responsive y operables por teclado;
- sin fuentes externas ni imágenes no autorizadas;
- estados vacíos honestos cuando falta contenido real.

La aplicación no inventa experiencia, proyectos, precios, testimonios ni canales. Fixtures sintéticos existen sólo en pruebas y desarrollo.

## Pruebas

- Unitarias: validación, estados, tokens, origen, IP, DTO y redacción.
- Integración con PostgreSQL real: autorización, borradores, concurrencia, límites, transacciones, migraciones y rollback.
- Contrato HTTP: REST, Local API mediante gateways, rutas Next, medios, sitemap y GraphQL cerrado.
- E2E contra build productivo: F1 a F4, sin JavaScript donde corresponda, teclado y axe.
- Gates: lint, typecheck, unit, integración, contrato, E2E, build, auditoría y migración desde cero.

## Despliegue

- Local: Compose en localhost, Node 24, PostgreSQL 18, datos sintéticos y migraciones versionadas.
- CI: PostgreSQL efímero, migración desde cero, build productivo y E2E.
- Staging: misma imagen candidata, TLS, acceso restringido, backup cifrado y restauración completa.
- Producción: requiere contenido real aprobado, política de privacidad/retención, hosting, almacenamiento de medios, backup externo y autorización humana.

`drizzle push` no se usa en CI, staging ni producción.

## Incrementos

1. **I1 - Intake seguro y base ejecutable:** admin, servicios mínimos, formulario, persistencia, bandeja, migraciones, CI y build.
2. **I2 - Operaciones:** observaciones, estados, motivos, eventos y filtros.
3. **I3 - Portafolio:** perfil, proyectos, medios, publicación, preview y sistema visual completo.
4. **I4 - Catálogo, contacto y SEO:** servicios completos, precios, contacto, metadatos, sitemap, robots, canonical, OpenGraph y datos estructurados.
5. **I5 - Candidato de liberación:** observabilidad, backup/restauración, retención, revisión manual WCAG, seguridad y staging reproducible.

Cada incremento termina con pruebas, revisión QA/Security, commit recuperable y checkpoint de rama/SHA.

## Condiciones de publicación

No bloquean I1-I4, pero sí publicación con datos reales:

- contenido profesional verificado;
- canales de contacto autorizados;
- catálogo, cobertura y precios reales;
- aviso de privacidad y política de retención;
- hosting, TLS y almacenamiento de medios;
- destino externo de backup y restauración ensayada.
